# Installation et exploitation — Père Blaise

## Portée

Les commandes ci-dessous sont des procédures pour l'exploitant. Elles ne constituent pas une autorisation de production acquise. Les deux spécifications restent les critères de revue. Aucun test ne doit pointer vers les vrais `Downloads`/`Documents` tant que la recette sur arbres temporaires et les permissions macOS ne sont pas validées.

Le 14 octobre 2026, un ancien conteneur `hermes-pere-blaise` de projet réel a été découvert actif avec un port local publié. Il a été arrêté sans supprimer son volume, puis remplacé après validation d'une copie en staging. L'ancien code est conservé sous `deployments/.archive/pere-blaise-20261014-pre-stage-182932`. La nouvelle composition réelle est healthy avec les seuls montages approuvés, sans port publié. Après validation finale de Clément et réception des notifications de la tâche manuelle sur les deux canaux, `weekly_enabled: true` a été écrit dans le runtime privé et le broker redémarré healthy. Aucune exécution n'était due le mercredi 14 octobre (`weekly_runs` et plans à zéro). Les commandes de recette ont utilisé uniquement des dossiers fictifs ; aucun document personnel n'a été classé.

## Installation et configuration initiale

1. Vérifier la source physique `~/workspace/hermes-knights-grail/pere-blaise`, son slug, `README.md`, `compose.yaml`, `config/`, `src/`, `tests/`. La guideline commune actuellement présente autorise ce chemin ; le passage `my-hermes` dans la spécification est historique. Ne pas modifier les guidelines communes sans approbation explicite.
2. Prévisualiser puis staged avec `scripts/deploy-stage-safe.sh --deploy-root "$HOME/Library/Application Support/HermesAgents/deployments" --budget-kib 2048 --preview`. Relire chemins et octets. Passer `--stage --confirmed-total-bytes N` avec le N affiché, puis vérifier le staging. L'activation exige le chemin exact `--activate-stage PATH`. Pour une mise à jour, arrêter les services et utiliser `--replace-stage PATH --archive-current PATH --confirm-services-stopped` ; l'ancien code est archivé sans suppression.
3. Créer un répertoire privé 0700 hors dépôt, par exemple `~/Library/Application Support/HermesAgents/runtime/pere-blaise`. Y déposer `broker.json` fondé sur `config/broker.example.json`, avec les trois racines physiques et les limites. Les chemins doivent être `/downloads`, `/documents`, `/backups`, `/state` **dans le conteneur**. Les IDs Telegram/Slack, canal Slack et propriétaire hebdomadaire restent dans ce fichier privé. Garder `weekly_enabled: false`.
4. Créer des fichiers 0600 `telegram.token`, `slack-bot.token`, `slack-app.token` et `planner.env`. Ne jamais saisir leur valeur dans Git, commande de shell visible, log ou ticket. `planner.env` contient `PERE_BLAISE_API_KEY` pour le broker ; le fichier d'environnement privé du planificateur contient `API_SERVER_KEY` avec la même valeur. Prévoir `paths.env` privé pour `PB_PLANNER_ENV_FILE`, `PB_HERMES_CONFIG`, `PB_DOWNLOADS`, `PB_DOCUMENTS`, `PB_BACKUPS`, `PB_PRIVATE_DIR`. Les racines hôtes sont des répertoires déjà existants ; ne monter ni `$HOME` entier ni dépôt.
5. Vérifier Docker Desktop, le partage des trois chemins et les autorisations macOS du propriétaire. Si macOS les demande, accorder à Docker Desktop les droits **Fichiers et dossiers** ciblés sur Downloads/Documents ; ne pas demander « Accès complet au disque » par défaut. Un test sur dossiers jetables ne démontre pas l'autorisation des dossiers réels. L'OAuth `openai-codex` doit être initialisé **dans le volume Hermes privé** par le propriétaire, puis contrôlé après redémarrage. Vérifier que le modèle `gpt-6-luna` avec `agent.reasoning_effort: low` et le volume d'automatisation sont autorisés par l'abonnement. Sans cela, laisser les services arrêtés.
6. Réutiliser le bot Telegram et l'app Slack existants après audit ; stopper l'ancien consommateur Telegram avant le nouveau. Vérifier le canal privé et les utilisateurs autorisés. Slack requiert `files:write` et, pour Socket Mode, un token `connections:write`.

`scripts/lifecycle.sh configure DOWNLOADS DOCUMENTS BACKUPS` crée les fichiers privés vides avec permissions strictes, sans afficher ni demander les tokens dans le dépôt. L'exploitant renseigne ensuite `broker.json`, les deux fichiers de clé interne identique et les tokens via son gestionnaire de secrets. `scripts/validate-private.py` refuse les allowlists absentes, les permissions trop larges et une tâche hebdomadaire activée sans `weekly-approval.json` privé portant `approved_by` et `manual_test_at`. `scripts/lifecycle.sh start|stop|restart|status|logs` utilise le même Compose ; `stop` conserve aussi les conteneurs et leurs logs.

### Informations à recueillir sans divulguer les secrets

- **Modèle** : le propriétaire a choisi `gpt-6-luna`, effort `low`, fournisseur `openai-codex`. Le fichier versionné est `config/planner.config.yaml` ; sa copie privée `planner.config.yaml` est montée en lecture seule dans le volume Hermes. `auth.json` déjà présent dans le runtime privé ne prouve ni sa validité ni l'accès au modèle. Faire un appel réel sur données fictives puis revérifier après redémarrage, sans configurer de clé API OpenAI.
- **Slack** : ouvrir l'app existante « Hermes — Père Blaise » dans [Your Apps](https://api.slack.com/apps), workspace `NexTarget-26`. Dans « OAuth & Permissions », vérifier le Bot User OAuth Token (`xoxb-…`) et les seuls scopes bot `app_mentions:read`, `chat:write`, `files:write` ; placer le token dans `slack-bot.token`. Dans « Basic Information > App-Level Tokens », retrouver le token Socket Mode (`xapp-…`) avec `connections:write` et le placer dans `slack-app.token`. Vérifier « Socket Mode » activé et « Event Subscriptions > Subscribe to bot events » contenant `app_mention`. Le canal privé `#agent-pere-blaise` existe et le bot en est membre. L'ID du canal et les IDs des seules personnes autorisées vont dans `broker.json` ; un ID membre se copie depuis son profil Slack, bouton « More > Copy member ID ». Aucune valeur de token ne doit être envoyée dans un message.
- **Deuxième personne autorisée** : le compte `elise.v.seguy@gmail.com` était absent du workspace lors de la recette ; Clément a choisi de le créer plus tard. Une fois le compte créé et invité dans le canal privé, relever son ID membre, l'ajouter seulement à `slack_allowed_user_ids` dans le `broker.json` privé, valider ce fichier et redémarrer le broker. L'invitation Slack seule ne donne pas accès à l'agent ; aucun changement de code ou nouveau bot n'est nécessaire.
- **Audit du 14 octobre 2026** : `scripts/check-channel-credentials.py PRIVATE_DIR` lit les fichiers 0600, interroge `getMe`/`getWebhookInfo`, `auth.test` et `apps.connections.open`, puis n'affiche que l'identité publique du bot, le statut du webhook, les scopes et l'hôte WebSocket ; il ne consomme aucun message. Après réinstallation de l'app existante, l'API Slack a confirmé les scopes bot `app_mentions:read`, `chat:write`, `files:write` et le scope Socket Mode `connections:write`. L'absence de webhook Telegram ne prouve pas l'absence d'un autre processus en polling ; une réponse retardée pendant l'arrêt du broker d'essai ne suffit pas non plus à le prouver.
- **Upload Slack** : la première requête `files.getUploadURLExternal` en JSON a répondu `invalid_arguments` sur ce workspace ; le même appel en `application/x-www-form-urlencoded` a obtenu un ticket. Le broker utilise ce format pour `files.getUploadURLExternal` et `files.completeUploadExternal`, avec la liste `files` sérialisée en JSON dans un champ formulaire, conformément aux [méthodes d'upload Slack](https://docs.slack.dev/reference/methods/files.getUploadURLExternal/). Ne jamais afficher l'URL signée du ticket ; un échec après transfert est incertain et ne doit pas être répété sans inspection du fil.
- **Telegram** : retrouver le bot existant dans la conversation vérifiée `@BotFather` avec `/mybots`, puis le token dans le gestionnaire de secrets ou auprès de l'exploitant actuel ; ne pas générer un nouveau token par défaut. Placer uniquement sa valeur dans `telegram.token`. Recueillir l'ID numérique des personnes autorisées et l'ID du chat privé destinataire de l'hebdomadaire dans `broker.json`. Après réception d'un message privé `/start` adressé au bot, un diagnostic local de `getUpdates` peut extraire seulement `from.id`, `chat.id` et `chat.type` ; ne pas afficher le token ni le texte des messages. Vérifier d'abord qu'aucun webhook ou autre processus ne consomme les événements ; conserver l'ancien système arrêté avant le premier démarrage du broker.
- **Configuration privée** : `broker.json` part de `config/broker.example.json`. Remplir `telegram_allowed_user_ids`, `slack_allowed_user_ids`, `slack_allowed_channel_id`, `weekly_owner` et `weekly_telegram_chat` ; conserver `identity_map: {}` sans liaison explicite d'identités et `weekly_enabled: false`. Le propriétaire désigne les personnes autorisées et la personne qui reçoit la notification hebdomadaire. Les chemins internes `/downloads`, `/documents`, `/backups`, `/state` restent ceux de l'exemple. Générer une seule clé interne aléatoire et l'écrire dans `planner.env` sous `PERE_BLAISE_API_KEY=`, et dans `planner-api.env` sous `API_SERVER_KEY=`, sans l'afficher. Les deux fichiers sont privés 0600. Durant la recette, `paths.env` pointe vers des arbres fictifs sous `/private/tmp`, jamais vers les dossiers personnels.

## Commandes Docker contrôlées

Depuis la copie de déploiement, avec `--env-file "$PRIVATE/paths.env"` :

```sh
docker compose --env-file "$PRIVATE/paths.env" config --quiet
docker compose --env-file "$PRIVATE/paths.env" up -d --build
docker compose --env-file "$PRIVATE/paths.env" ps
docker compose --env-file "$PRIVATE/paths.env" logs --no-color --tail=100
docker compose --env-file "$PRIVATE/paths.env" restart
docker compose --env-file "$PRIVATE/paths.env" down
```

`down` ne reçoit jamais `--volumes`. Les deux volumes natifs sont `hermes-pere-blaise-data` et `hermes-pere-blaise-broker-data`. Les healthchecks doivent être `healthy` avant tout test de canal. Aucun port n'est publié. Une image s6 Hermes peut garder le conteneur en marche alors que le gateway est malade : le healthcheck Hermes sonde désormais `GET /health` sur l'API, pas seulement le superviseur. Vérifier également l'API authentifiée `/v1/toolsets` (compter les entrées `data` avec `enabled: true`), un appel de planification de test, puis le modèle/OAuth. Vérifier qu'aucun toolset n'est activé et qu'un appel sans clé renvoie 401. Le test jetable du 14 octobre a montré qu'une clé interne factice à caractères répétés empêche l'API de démarrer alors que `gateway status` peut rester healthy ; utiliser une clé aléatoire. Le timeout du healthcheck reste à 30 secondes pour éviter un échec lié au démarrage lent sur ce Mac.

F-013/F-014 sont reportées. Ne lancer aucune ancienne commande de rapprochement, correction ou effacement sur les tables d'apprentissage. Les tables et backups préexistants restent conservés ; les fonctions correspondantes refusent l'appel dans cette version.

## Tâche hebdomadaire

La configuration `weekly_enabled: false` est le défaut. Le déclencheur interne est dimanche 17 h `Europe/Paris`. Au redémarrage, il accepte une seule exécution du dernier dimanche manqué avant lundi 17 h exclus ; aucun rattrapage plus ancien et aucun doublon grâce à la clé du dimanche dans SQLite. Il tente d'abord les deux notifications, exécute une analyse, puis tente les deux résultats. Il n'appelle jamais `range`. Après démarrage des services et audit des vrais canaux sur **dossiers fictifs**, exécuter manuellement `docker compose --env-file "$PRIVATE/paths.env" exec broker python /app/scripts/manual-weekly.py` avec `weekly_enabled: false`. Cette commande refuse un destinataire Telegram hors allowlist, envoie départ/résultat sur les deux canaux et affiche seulement les canaux en échec. Vérifier `weekly_owner`, le lancement, le résultat, l'unicité, et l'absence de mouvement, puis présenter cette preuve à Clément. **Activer `weekly_enabled: true` seulement après sa validation finale** et un redémarrage contrôlé. Un échec d'un canal n'empêche pas l'autre ; examiner le journal par ID d'incident. Aucun crontab n'est installé.

## Sauvegarde et restauration

Les backups de fichiers classés sont sous `PB_BACKUPS/<plan-id>` et ne sont jamais purgés automatiquement. Pour SQLite broker, `scripts/state-backup.py backup --source SOURCE --destination NOUVEAU.db` utilise l'API de backup SQLite, fait `integrity_check` et écrit un SHA-256. `restore --dry-run` affiche les chemins ; `restore` exige la source avec `.sha256`, une destination absente et un broker arrêté. Vérifier à nouveau `integrity_check`, puis démarrer le broker et vérifier les états de journal ; aucune vérification d'apprentissage n'est requise puisque F-013/F-014 sont reportées. Ne pas copier à chaud un `state.db` en WAL depuis un bind mount macOS. Le volume Hermes natif, sa configuration et son OAuth sont exportés à froid et chiffrés hors dépôt. Le flux a été exercé seulement avec volumes et secrets factices le 14 octobre 2026.

`scripts/lifecycle.sh backup --path "$HOME/Library/Application Support/HermesAgents/snapshots/pere-blaise/<id>" --dry-run` affiche le périmètre. Après contrôle, `--confirm --recipient age1...` crée une sauvegarde chiffrée `age` des deux volumes et de la configuration privée, avec manifeste SHA-256, après arrêt. `restore --path ... --dry-run`, puis `--confirm --identity /chemin/prive/identite` ne restaure que vers des volumes et un répertoire privé **absents**. Pour la recette jetable, `scripts/volume-backup.sh` accepte `--disposable --private-root /private/tmp/pb-test-... --hermes-volume pb-test-... --broker-volume pb-test-...` avec un `--path` sous `/private/tmp/pb-test-...` ; les volumes sources et cibles doivent être distincts et arrêtés. La restauration rejette les archives à lien/traversée et UID/GID inattendus, vérifie SHA-256, permissions privées et `PRAGMA integrity_check`, puis requiert un redémarrage du broker pour confirmer l'état. Un essai a révélé une propriété UID 0 impropre ; le correctif a été validé sur de nouvelles cibles avec une transaction appliquée sans rejeu. Un échec peut laisser une cible jetable partiellement créée : l'inspecter avant toute suppression ou nouvel essai. Le dossier des backups de classement n'est ni copié ni purgé par ce flux. `age` v1.3.2 officiel a été vérifié par SHA-256 puis installé pour cet utilisateur dans `~/Library/Application Support/HermesAgents/bin` après échec de Homebrew lié aux permissions globales ; le script le cherche à cet endroit si `age` n'est pas dans `PATH`. L'identité de déchiffrement reste hors dépôt. Voir la [documentation officielle age](https://github.com/FiloSottile/age/blob/main/README.md).

## Mise à jour, migration et rollback

Relever le digest/version `docker image inspect` et `hermes --version` avant changement ; l'image de référence testée annonce v0.21.6/upstream `818c13be`. Ne pas remplacer un digest par un tag flottant. Arrêter broker/Hermes, sauvegarder SQLite via API et le volume Hermes à froid, créer un staging, exécuter tests et `docker compose config`, puis démarrer une recette sur volumes et dossiers temporaires. Dans un conteneur broker hors service monté sur son volume natif et un répertoire de backup privé distinct, `/app/scripts/migrate-state.py upgrade --database /state/plans.sqlite3 --state /state --backup /backup/NOUVEAU.db --dry-run`, puis la même commande sans `--dry-run`, crée un backup SQLite cohérent, vérifie son SHA-256 et `integrity_check`, refuse un plan `applying` ou un journal non terminé, et passe le schéma 1→2 sans toucher aux anciennes données d'apprentissage. Le retour 2→1 utilise `rollback` avec un **autre** chemin de backup absent ; les deux sens ont été testés localement. Cette migration est explicite, hors ligne, et ne doit pas être lancée pendant un service actif. En cas d'échec de mise à jour, conserver le déploiement courant et l'archive de code ; restaurer seulement une base de schéma compatible. Les évolutions de prompt/skill prennent effet à une nouvelle session. Le retour arrière du vrai volume Hermes/OAuth et d'un nouveau digest n'a pas été exercé ; toute mise à jour de production attend cette recette.

## Désinstallation et suppression complète

Désinstallation conservatrice : `scripts/lifecycle.sh uninstall --dry-run`, puis `--confirm-archive CHEMIN_EXACT` sous `.archive/pere-blaise-*`. Le script arrête les services, exporte leurs logs dans le runtime privé, retire les conteneurs **sans** `--volumes` et archive le code. Il conserve volumes, backups, secrets, journaux et les vrais `Downloads`/`Documents`. Ne pas employer `rsync --delete` ni supprimer l'ancien déploiement sans validation humaine explicite après aperçu.

Suppression complète : `scripts/lifecycle.sh purge --dry-run` affiche les chemins, tailles des volumes et archives éventuelles. Le flux d'exécution exige `--confirm "PURGE pere-blaise" --reviewed`, un terminal interactif et la recopie exacte des trois chemins ; il refuse toute archive restante et une racine de backup configurée hors du périmètre fixe. Les deux racines `Downloads` et `Documents` restent exclues. Ne jamais lancer ce flux sur le runtime existant sans revue humaine explicite du manifeste affiché.

## Incident

Un journal `APPLYING` est rapproché au démarrage. Si l'état est `BLOCKED_RECOVERY`, stopper les services, conserver backup, source et cible, comparer les hashes avec l'exploitant et ne pas relancer `range`. Un timeout Telegram/Slack après transmission est une livraison incertaine : vérifier côté canal avant toute nouvelle demande, afin d'éviter un doublon. Une erreur OAuth/quota bloque l'analyse sans fournisseur de repli. Révoquer les tokens seulement en cas de fuite ou d'impossibilité de stopper l'ancien consommateur, puis mettre à jour les fichiers privés 0600 et retester les deux canaux.

Les événements Telegram et Slack reçus sont marqués dans `/state/ingress.sqlite3` avant traitement, puis marqués terminés après la réponse. Ce journal privé garde les IDs terminés 30 jours par défaut et empêche leur répétition après redémarrage. Un arrêt entre le marquage initial et la réponse peut laisser un événement sans résultat ; le propriétaire peut alors renvoyer sa commande après avoir vérifié le canal, mais le broker ne rejoue pas automatiquement une action potentiellement dangereuse. Ce fichier fait partie du volume broker sauvegardé et restauré.
