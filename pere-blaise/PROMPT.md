# Prompt de réalisation — Père-Blaise

Tu es Codex dans le dépôt `hermes-knights-grail`, pour réaliser **entièrement** l'agent `pere-blaise`. Ce prompt est autonome ; ne suppose aucune mémoire de la session de cadrage.

## Sources et ordre de travail

1. Lis `AGENTS.md` à la racine, tout `AGENTS.md` applicable, `README.md`, `docs/agent-creation-checklist.md`, puis `pere-blaise/SPECIFICATIONS_FONCTIONNELLES.md` et `pere-blaise/SPECIFICATIONS_TECHNIQUES.md` **avant de modifier un fichier**. Lis les politiques, le code et les tests déjà présents dans `pere-blaise/` ; traite-les comme une base non validée, pas comme une preuve de fonctionnement.
2. Consulte la documentation et la révision **réellement disponible** de Hermes, notamment Docker/macOS/SQLite, installation, configuration, modèle `openai-codex`, gateway/API, canaux, toolsets, cron, skills, mémoire et sécurité. La spécification a été cadrée contre la révision locale `bd0affe5e5f723579df8902852f5d0c47795f355` (`v0.21.4+canary.20261003T070620Z`) ; vérifie le digest/version de l'image effectivement retenue et adapte sans inventer d'API. Garde toutes les sources du projet séparées du cœur Hermes ; utilise ses interfaces publiques et documentées. Toute proposition de patch du cœur exige une justification et une décision explicite.
3. Reprends **uniquement** les « Modifications proposées aux guidelines » explicitement approuvées par l'utilisateur après le cadrage. Si aucune approbation n'est visible, n'édite pas `AGENTS.md`, la checklist ou d'autres guidelines communes. La règle actuelle de source sous `~/workspace/my-hermes/<slug>` peut alors empêcher un déploiement depuis ce dépôt : ne la contourne pas et expose précisément le blocage, tout en réalisant et testant les parties indépendantes.

## Livraison attendue

Implémente le projet complet : code de scanner, registre de plans, routeur, relai Telegram et Slack, envoi natif de documents, exécuteur transactionnel versionné, backups vérifiés avant tout déplacement, rollback et reprise sur journal, suivi local par hash des fichiers `a_trier`, erreurs stables, planification du dimanche 17 h Europe/Paris, prompts/skill, configuration sans secrets, infrastructure Docker Desktop macOS, scripts de cycle de vie, tests et documentation opératoire. Mets à jour la politique et les documents d'agent pour refléter les deux spécifications ; conserve les trois fichiers de cadrage comme référence.

Respecte les règles décisives : le modèle ne voit que les noms de fichiers `Downloads` et les dossiers `Documents`, jamais les octets, hashes ou noms de documents déjà classés ; seuls les composants locaux isolés accèdent aux trois racines nécessaires ; aucune création de dossier hors `a_trier` initial ; aucune suppression/modification de document préexistant ; un plan vaut 30 minutes et est personnel à son auteur, annulé par un nouveau plan ou les changements prescrits ; `range <ID>` est la seule validation de mouvement ; `envoie` désambiguïse **tous** les noms avant transfert ; aucun envoi vers un autre canal ; aucune purge automatique des backups. Réutilise le bot Telegram et l'app Slack existants s'ils satisfont les contrôles, sans les supprimer ni les recréer par défaut. Ne demande jamais les tokens dans le dépôt ou les logs.

Le dépôt doit contenir un tableau de traçabilité `F-001…F-018 → fichiers réalisés → tests → résultats`. Chaque script d'installation/déploiement suit les garde-fous de `AGENTS.md` : chemins physiques et slug, refus des sources dangereuses, aperçu et budget avant copie, absence de suivi des symlinks, staging, aucune suppression `--delete` sans validation explicite. Les scripts de désinstallation préservent **données, volumes, backups et secrets** par défaut ; seule une commande distincte de suppression complète, avec aperçu exact et confirmation explicite, peut les effacer. Elle ne touche jamais `Downloads` ou `Documents`.

Teste réellement les chemins critiques, y compris erreur après le premier déplacement, coupure/redémarrage, restauration SQLite, expiration/invalidation de plan, propriétaire croisé Telegram/Slack, envoi 0/1/N, hash après renommage, limites de taille, permissions négatives, échec de canal et tâche hebdomadaire. Vérifie `docker compose config`, healthchecks, montages et volume natif SQLite. Sur Docker Desktop macOS, exécute des tests d'intégration réels **dans la mesure où l'environnement le permet** ; ne lance jamais un essai sur les vrais fichiers personnels. Si Docker Desktop, OAuth, tokens, comptes de test ou permissions macOS ne sont pas accessibles, indique exactement les commandes non exécutées et les prérequis manquants, sans inventer de réussite. Ne mets pas le service en production ni n'active la tâche planifiée sans les validations exigées par les consignes du dépôt.

Documente installation, configuration initiale, démarrage, arrêt, redémarrage, état, logs, mise à jour/migration/rollback, sauvegarde, restauration, désinstallation conservatrice et suppression complète. Termine par un bilan factuel : fonctionnalités livrées, fichiers importants, commandes de test réellement exécutées et résultats, exigences non couvertes, limites, risques restants et étapes manuelles d'activation.
