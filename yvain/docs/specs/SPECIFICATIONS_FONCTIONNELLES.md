# Yvain — spécifications fonctionnelles

Décisions : 26–27 octobre 2026. Statut : cadrage validé pour le développement, mise en service conditionnée aux contrôles décrits ci-dessous.

## 1. Besoin, résultat attendu et source de vérité

Yvain reprend l'agent QA existant dans `yvain/`. Il recettera la version Android de NexTarget-app issue de `origin/staging` contre NexTarget-server construit depuis **son propre** `origin/staging`. Il utilisera l'émulateur Android du Mac, le staging Docker local, le changelog applicatif pour repérer les nouveaux tickets et les 55 cas actuellement définis dans `NexTarget-app/docs/tests/cahier_recette.yaml`. Le Markdown du même dossier est la représentation générée à contrôler, et non une seconde source éditable. Le nombre de cas est une photographie au 26 octobre 2026 : à chaque campagne, Yvain prend le cahier du commit applicatif recetté et enregistre sa version et son nombre de cas.

Une campagne comporte deux phases ordonnées : **(1) nouveaux tickets** repérés dans les lignes ajoutées au changelog depuis le dernier SHA applicatif recetté, avec leurs cas du cahier ; **(2) non-régression complète** sur chaque cas du cahier figé au SHA testé, uniquement si tous les cas de la première phase ont réussi. Un défaut confirmé pendant la première phase interrompt la campagne avant la phase complète ; un défaut confirmé dans la seconde produit aussi une issue GitHub. Un cas sans automatisation, précondition ou oracle vérifiable est déclaré bloqué avec une raison et une demande d'action ; il n'est jamais compté comme réussi. Yvain ne modifie ni le code ni le cahier de NexTarget-app ou NexTarget-server ; seules les issues GitHub décrites ici sont une écriture autorisée. Les évolutions visibles doivent avoir mis à jour le YAML et le Markdown généré pendant l'implémentation de la fonctionnalité.

Objectifs mesurables : 100 % des nouveaux tickets détectés ont une sélection de cas ou un blocage de couverture explicite ; 100 % des IDs du cahier apparaissent une fois dans le bilan final, avec `non_exécuté` et sa cause lorsque la seconde phase n'a pas été atteinte ; 100 % des résultats « réussi » sont reliés à une assertion et à une preuve ; le rapport contient les SHA de l'app et du serveur, l'AVD, les versions d'outils, la durée et l'origine du déclenchement ; aucun statut GitHub `success` n'est publié si un cas échoue, fluctue, manque de couverture ou reste bloqué ; une synthèse et le rapport Markdown en pièce jointe arrivent dans Slack après chaque campagne, y compris une campagne bloquée ou interrompue, sous réserve de la disponibilité de Slack.

## 2. Périmètre, exclusions et acteurs

**Inclus.** Contrôle quotidien local des nouveaux commits `staging`, demande manuelle via Slack soumise au même contrôle de changement, lecture du changelog et vérification de cohérence du cahier, recette des nouveaux tickets puis non-régression complète sous condition de succès, construction de l'APK DEBUG au commit exact, lancement du serveur de staging et remise à zéro de sa base isolée, exécution des scénarios Android/Maestro et contrôles complémentaires déterministes, collecte de preuves, rapport par cas et global, statut GitHub sur le commit applicatif, création automatique d'issues GitHub pour les défauts produit confirmés, notification Slack et exploitation du runtime Yvain.

**Exclus.** Modification du code, du cahier ou de la configuration des dépôts NexTarget par Yvain, hormis la création d'issues GitHub autorisée ici ; déploiement de production ; accès à des comptes, secrets ou données de production ; lancement de tests Coach/OAuth nécessitant des comptes de recette tant que ceux-ci n'existent pas ; validation humaine implicite d'un rendu visuel subjectif ; blocage automatique d'une fusion GitHub tant que le statut Yvain n'a pas été explicitement configuré comme contrôle requis par le propriétaire.

| Acteur | Rôle et accès |
| --- | --- |
| Propriétaire humain (l'utilisateur) | Seul demandeur Slack autorisé, seul lecteur des preuves détaillées, valide les changements de politique ; la création d'issues pour défauts confirmés est autorisée par cette spécification. Crée lui-même les deux branches `staging`. |
| Yvain / gateway Hermes | Reçoit les demandes dans le canal privé `#agent-yvain`, accuse réception, consulte les rapports, tient une mémoire limitée aux décisions durables confirmées. |
| Runner macOS dédié | Exécute la campagne bornée, contrôle Docker Desktop, Flutter, `adb`, Maestro et les Git worktrees temporaires. N'accepte aucune commande arbitraire depuis Slack. |
| GitHub NexTarget-app | Source des commits, destinataire du statut de recette du SHA `staging` et des issues de défaut mobile/intégration ; lecture Git, `statuses:write` et `issues:write` bornés. |
| GitHub NexTarget-server | Source de `origin/staging` et destinataire des issues de défaut serveur confirmé ; lecture Git et `issues:write` bornés. |

Le canal `#agent-yvain` est **privé**, réservé au propriétaire et à l'application Slack dédiée. Aucun DM ni autre canal n'est utilisé. Les identifiants Slack exacts et l'identité GitHub technique sont des paramètres privés à renseigner lors de l'installation, sans changer ce contrat.

## 3. Parcours et règles de décision

### Campagne quotidienne

À 09 h, fuseau `Europe/Paris`, lorsque le Mac est disponible, le contrôle local interroge `origin/staging` de NexTarget-app **et** NexTarget-server. Il compare la paire `(SHA app, SHA serveur)` à celle de la dernière campagne de recette engagée. Si les deux SHA sont inchangés, il consigne un contrôle sans campagne, sans reset ni nouvelle notification. Si l'un des deux a changé, il recettera la **dernière paire** observée ; le rapport répertorie les commits intermédiaires de chaque dépôt. Un contrôle manqué pendant l'arrêt ou la veille du Mac est repris au prochain réveil/démarrage ; il ne lance pas des campagnes de rattrapage concurrentes. Une seule campagne tourne à la fois. Si un nouveau SHA arrive pendant une campagne, la dernière paire est conservée en attente.

### Demande Slack

Le propriétaire mentionne Yvain dans `#agent-yvain` et demande une recette. Yvain vérifie l'identité et le canal, crée une demande structurée, rend un identifiant de demande et indique si elle est en attente ou déjà en cours. Le runner compare la paire des SHA `origin/staging` à celle de la dernière campagne engagée : si les deux sont inchangés, **aucune nouvelle recette ne démarre**, même sur demande manuelle et même si le dernier verdict est défavorable. Yvain répond alors avec l'identifiant et le verdict du dernier run, ainsi que sa référence locale si le rapport est encore conservé ; si le rapport a expiré, il le dit explicitement. Il ne publie pas de nouveau statut GitHub ni de pièce jointe répétée. Si l'un des SHA a changé ou si aucune campagne n'a encore été engagée, la campagne manuelle suit les deux phases dans le même ordre que le contrôle quotidien. La prise en charge doit commencer dans la minute lorsque le Mac, Docker et Hermes sont disponibles ; sinon Yvain indique le blocage ou traite la demande au prochain démarrage. Une demande répétée avec le même identifiant ne lance pas deux campagnes.

### Exécution et résultat

Le runner fige les SHA app et serveur et refuse une branche absente. Il vérifie le cahier YAML, sa concordance avec le Markdown généré, les prérequis, l'espace disque, l'AVD et les versions d'outils. Il construit le serveur avec `scripts/staging_qa.sh up --branch staging`, contrôle `/ready` et le SHA dans `/health`, puis construit l'APK DEBUG depuis un worktree applicatif détaché au SHA exact. Il rétablit les fixtures staging et l'état local Android avant chaque cas lorsque le scénario le demande. Les actions de reset sont autorisées **uniquement** sur le projet Compose et l'AVD de recette dédiés.

La phase « nouveaux tickets » extrait les identifiants `NT-XXX` des lignes ajoutées à `CHANGELOG.md` depuis le dernier SHA applicatif recetté, les déduplique et les relie au backlog et aux cas du YAML. **Pour la première campagne**, la comparaison est `origin/main...origin/staging` de NexTarget-app, au SHA `staging` figé pour la recette. Plusieurs cas peuvent couvrir un ticket ; un cas peut couvrir plusieurs tickets, mais l'appariement est explicite et vérifiable. Un ticket sans cas ou oracle exécutable est `bloqué_couverture` et empêche la phase complète. Yvain termine les tests de **tous** les nouveaux tickets même si un défaut est confirmé sur l'un d'eux, puis arrête la campagne avant la phase de non-régression si un résultat n'est pas `réussi`. Si aucun ticket nouveau n'est détecté malgré un changement de commit, Yvain lance directement la phase complète. Si la phase des nouveaux tickets réussit, la phase complète réexécute **tous** les cas du cahier, y compris ceux déjà testés dans la première phase, pour vérifier la non-régression.

Chaque cas exécuté produit un état parmi `réussi`, `échoué`, `instable`, `bloqué_prérequis`, `bloqué_couverture` et `erreur_infrastructure` ; `non_exécuté` marque les cas restants lorsque la phase complète n'a pas commencé, avec motif et phase responsable. Un premier échec fonctionnel est rejoué une fois après reset ; deux échecs comparables confirment un défaut produit et conduisent à une issue GitHub. Un succès au second essai devient `instable` et bloque la phase complète, mais ne crée pas d'issue pour un défaut non confirmé. Une panne d'outil ou de connecteur, un prérequis absent et une lacune du cahier sont signalés sans être qualifiés de bug produit. Les assertions techniques Flutter/API peuvent compléter un parcours, mais ne remplacent pas une preuve utilisateur sur émulateur quand le cahier décrit une interaction mobile. Une attente visuelle qui ne dispose pas d'oracle automatique fiable reste bloquée ou exige une validation humaine documentée.

Le verdict global est `réussi` seulement si la phase des nouveaux tickets applicable et **tous** les cas de la phase complète ont réussi ; `échoué` s'il existe un échec ou une instabilité ; `bloqué` en présence de prérequis ou de couverture manquants sans échec produit ; `erreur` lorsque l'infrastructure empêche de conclure. Le statut GitHub `Yvain/recette` est `pending` au début, `success` pour `réussi`, `failure` pour `échoué`, `error` pour `bloqué` ou `erreur`. Le descriptif court et l'URL/identifiant de rapport identifient le run et la dernière phase atteinte ; une défaillance de publication est conservée en attente de nouvelle tentative. La publication du statut est autorisée depuis le 26 octobre 2026.

Pour chaque défaut produit reproductible, Yvain crée automatiquement **une issue par défaut distinct** dans le dépôt concerné (`NexTarget-app` pour le mobile, `NexTarget-server` pour le serveur), avec ticket, phase, deux SHA, environnement, étapes, attendu/observé et preuves expurgées. Un défaut d'intégration dont la responsabilité n'est pas encore attribuable est signalé dans NexTarget-app comme point d'entrée de triage, sans affirmer que le code app est la cause. Avant création, il recherche une issue ouverte équivalente et conserve un identifiant de défaut pour rendre les réessais idempotents ; il lie l'issue existante au rapport au lieu d'en créer une seconde. En cas d'échec ou de réponse ambiguë de GitHub, il conserve l'opération en attente, relit les issues avant tout nouvel essai et alerte le propriétaire. Les rapports locaux et captures brutes ne sont pas publiés dans l'issue.

### Restitution et interventions humaines

Le rapport local horodaté contient la sélection des nouveaux tickets, les résultats par phase et une ligne par ID du cahier dans le bilan final, le détail des étapes exécutées, attendu/observé, preuves et limites, les changements repérés depuis la précédente paire recettée, les URLs des issues créées ou réutilisées ou leur état `issue_en_attente`, la version des sources et des outils, le verdict et les actions proposées. La synthèse Slack indique les nombres par état, la phase atteinte, le verdict, les principaux blocages et l'identifiant du run. Le rapport Markdown est joint comme fichier natif Slack ; les captures/logs restent locaux et sont accessibles au seul propriétaire. Si Slack échoue, la campagne et son rapport restent consultables ; l'envoi est repris sans rejouer les tests. Si GitHub échoue, seuls le statut ou la création d'issue en attente sont repris ; Yvain communique ensuite l'URL publiée dans le fil Slack. Les événements de lancement, reset, test, décision et livraison sont journalisés sans secrets.

Le propriétaire intervient pour fournir ultérieurement des comptes et fixtures connectés, corriger le cahier dans le dépôt applicatif, valider un rendu sans oracle automatique, résoudre un problème de quotas ou de credentials, et autoriser toute suppression complète. Aucune résolution de blocage n'est inventée par Yvain.

## 6. Qualité de service et scénarios de recette de bout en bout

La campagne quotidienne se lance à 09 h locale si le Mac et Docker sont disponibles ; une interruption est visible au prochain démarrage. Une demande Slack est prise en charge en une minute en régime nominal. La limite de 120 min produit un verdict `erreur` ou `bloqué` explicite, jamais `réussi`. Les coûts LLM sont bornés au dialogue et à l'analyse demandée ; les tests et la synthèse chiffrée sont déterministes. Aucun fournisseur de modèle alternatif ni clé API OpenAI implicite. Les rapports sont lisibles en Markdown français, avec états textuels et pas seulement des couleurs.

Scénarios à valider :

1. **Nominal quotidien** : nouveau SHA app ou serveur et deux branches présentes ; nouveaux tickets détectés dans le changelog et tous testés avec succès, puis 55 IDs inventoriés et retestés, cas connectés bloqués, rapport local, statut GitHub `error`, synthèse et pièce jointe Slack. Paire inchangée : simple contrôle local, aucune campagne.
2. **Nominal manuel** : commande du propriétaire avec changement sur l'une des deux branches : même séquence en deux phases ; sans changement : réponse avec le dernier verdict, sans run, reset, nouveau statut ni nouvelle pièce jointe. Commande d'un tiers ou d'un autre canal refusée.
3. **Défaut nouveau / non-régression** : défaut confirmé sur un nouveau ticket, les autres nouveaux tickets sont terminés puis la phase complète est omise ; une issue est créée dans le dépôt concerné. Si la première phase réussit, la non-régression complète démarre et crée une issue pour chaque défaut confirmé, sans doublon. Échec puis succès au second essai donne `instable`, sans issue de bug certain.
4. **Échec de connecteur** : Slack indisponible puis rétabli ; rapport/statut restent conservés, livraison reprise une fois. Variante GitHub indisponible : statut réessayé sans relancer l'AVD.
5. **Redémarrage** : arrêt de Docker Desktop ou du Mac au milieu d'un run, puis retour ; run interrompu identifiable, aucun faux succès, demande en attente reprise selon la règle de concurrence.
6. **Restauration** : sauvegarder runtime et rapports, restaurer sur un environnement isolé, vérifier mémoire/session et ancien rapport, puis reconstruire le staging synthétique.
7. **Sécurité** : branche absente, SHA divergent, écriture du code NexTarget refusée, création d'issue limitée aux deux dépôts autorisés, autre AVD/Compose non affecté, secret absent des logs, de Slack et des issues.
8. **Sans ticket nouveau** : changement de SHA sans nouvel ID dans les lignes ajoutées au changelog ; phase complète immédiate, sans campagne vide ni faux succès.

## 7. Décisions et hypothèses résiduelles

Décisions du propriétaire : contrôle local quotidien et demande Slack, sans recette si aucune des deux branches `staging` n'a changé depuis la dernière campagne ; création des branches `staging` par lui-même ; nouveaux tickets du changelog d'abord, comparés entre `origin/main` et `origin/staging` pour la première campagne, tous terminés avant décision, puis cahier complet seulement si tous passent ; sans ticket nouveau, cahier complet immédiat ; issues GitHub automatiques dans le dépôt concerné pour défaut confirmé ; reset staging autonome ; absence actuelle de comptes connectés ; canal et preuves réservés à lui seul ; aucun changement de code ou de cahier NexTarget par Yvain ; envoi Slack automatique ; rapports locaux et pièces jointes Slack Yvain supprimés à 30 jours, preuves locales à 14 jours, mémoire confirmée ; 09 h Europe/Paris, une campagne, 120 min, dernière paire de SHA en attente ; statut GitHub automatique ; rapport local joint à Slack. La conservation des pièces jointes Slack pendant 30 jours a été confirmée le 27 octobre 2026.

À fournir lors du provisionnement, sans réinterpréter le besoin : IDs du workspace, du canal privé et de l'utilisateur Slack ; identité GitHub limitée aux statuts applicatifs et aux issues des deux dépôts ; AVD exact ; chemins des dépôts ; confirmation que l'image Hermes installée offre les interfaces vérifiées dans les spécifications techniques. L'absence de l'un de ces éléments bloque l'activation et produit un diagnostic de pré-vol. Les branches `staging` n'existaient pas sur GitHub lors de l'inspection du 26 octobre 2026 : leur création est un prérequis utilisateur, pas une action de Yvain. La capacité du bot à supprimer **ses propres** pièces jointes doit être vérifiée sur un fichier de test avant activation ; si le workspace l'interdit, l'activation reste bloquée jusqu'à correction des droits ou nouvelle décision du propriétaire.
